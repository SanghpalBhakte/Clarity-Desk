# Clarity Desk — Architecture (CD-01, 2026-10-28; line numbers removed 2026-11-03 because they drift: search by name)

Offline-first PWA for students. Vanilla JS, no build step, no framework. `localStorage` is the source of truth; Firebase is optional.
Deeper history and bug-fix intent: `PROJECT_MEMORY.md`. Known issues: `docs/AUDIT.md`.

## Files
- `index.html` (~480 lines): shell, nav, modal templates, theme bootstrap in `<head>`. Loads `firebase-config.js?v=N`, then `app.js` as a module. The Firebase compat SDK 10.8.0 (app, auth, firestore, ~150 KB) is not a plain script tag: an inline loader (`cdLoadFirebaseSdk`, copied in `404.html`) starts it alongside `app.js` only when `cdFirebaseWanted`: `cos_cloud_signed_in` is `true` (local-only, written on every auth state change; not in backups), or the key is missing and an older version left signs of a sign-in (`cos_sync_last_pushed`, `cos_signin_seen`, a `firebase:authUser:` key), or the address is an email sign-in link (`oobCode`), or a Google redirect is coming back (`cos_auth_redirect` in sessionStorage). `init()` calls `initFirebase` after that download (again on `online` if it failed). Signed-out phones load it only when sign-in is opened (`loginWithGoogle` / `showEmailSignInModal` await `loadFirebaseSdk`; Settings and the welcome Log in call `warmFirebaseSdk` first, online and not on data saver, so Google's popup still opens inside the tap).
- `app.js` (~19k lines, ~0.96 MB raw, ~260 KB gzip): everything else. No modules; one global scope. `data.js` (fallback timetables, quick links, Dev Notes), `desk-assistant.js` (lazy, Ask Desk answers; precached by `sw.js` so it works offline), `scanners.js` (lazy, attendance photo scan and syllabus scan; precached the same way), `timetable-ocr.js` (lazy, the timetable photo parsers; precached the same way), `deadline-import.js` (lazy), `welcome-tour.js` (lazy, the Explore tour), `vendor/jszip.min.js` (lazy).
- `style.css` (6.7k lines): themes via CSS variables, responsive rules.
- `sw.js`, `manifest.json`: PWA. `404.html` carries its own copy of the head bootstrap (keep in sync).
- `ai-proxy/` (Cloudflare Worker): Gemini/Groq/Workers-AI proxy; origin allow-list, per-user/per-IP rate limits, optional Firebase ID token.
- `workers/feedback/` (Cloudflare Worker, deployed by hand, not by `ship`): relays the Settings "Tell me what breaks" form to a private Telegram chat. Secrets `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`; origin allow-list, 1.2 MB body cap, 5/min per-IP limit, one retry on a Telegram hiccup. `POST /telegram` is Telegram's webhook (secret header, `TELEGRAM_WEBHOOK_SECRET`): it replies to anyone who messages the bot. `brand-bot.sh` sets the bot's name, logo, description and webhook. Client side is `FEEDBACK_URL` + `openFeedbackForm` / `submitFeedback` in `app.js`; while `FEEDBACK_URL` is empty (or sending fails) the old prefilled GitHub issue link (`bugReportUrl`) is used.
- `push-worker/` (Cloudflare Worker + D1): closed-app reminders via Web Push. Tables `devices`, `reminders`; anonymous device id, no account data.
- `scripts/ship.mjs`: bump cache version, `npm test`, commit, Dev Notes, push, `firebase deploy`, live smoke test. Run in batches (when the owner says ship; urgent fixes at once): merging a PR to `main` publishes nothing. Dev Notes carry no version label; the cache number stays internal and `devNoteText()` hides the old "(vN)" on display.
- `tests/`: ~56 Node `verify_*.mjs` (run by `npm test`; they read `app.js` source and eval parts of it under a mocked browser, no real browser), Playwright specs (visual, PWA smoke, mobile, post-deploy smoke, core flows: add task / mark attendance / sync reload in `core-flows.spec.ts`, run in CI by `npm run test:sync-flows`), `release-check.mjs`.
- `.github/workflows`: `test.yml` (npm test + photo check + pwa-smoke on push/PR), `live-check.yml`, `ai-models.yml` (daily: `scripts/check-ai-models.mjs` checks the AIService model IDs are still offered; needs `GEMINI_API_KEY`/`GROQ_API_KEY` repo secrets).

## Boot and load
- Service worker (`sw.js`) never answers same-site `/__/` requests (Firebase reserved pages: `/__/auth/handler` for sign-in on claritydesk.web.app, `/__/firebase/init.json`); they always go to the network.
- Firebase Hosting serves two sites from `.` (targets `app` = claritydesk, plus campusos). `index.html` points at `app.js`/`style.css`/`data.js` on jsDelivr pinned to a commit hash, with local `?v=N` fallback on error.
- `ship.mjs` rewrites the `?v=N`, the pinned commit and `CACHE_NAME` (`clarity-desk-vN`) together.
- Service worker: precaches shell + app files; `index.html`, `app.js`, `style.css` and `data.js` must all be saved or the new version does not install (the old one keeps serving; `isCoreAsset`), the rest is best effort. Network-first with a 3 s timeout for navigation/JS/CSS (then cached copy; after one slow answer, 30 s of cache-first); stale-while-revalidate for other assets; skips Firebase/Google API and Groq traffic. The Firebase SDK files (`www.gstatic.com/firebasejs/`) are saved on first use, not precached; `activate` copies them from the old caches into the new one before deleting the old ones, so a signed-in phone keeps syncing offline after an update. Handles the `share-target` POST (WhatsApp deadline import).

## State and storage (all `cos_*` keys; the `KEY_*` constants are at the top of `app.js`)
- Profile/tasks: `cos_profile`, `cos_custom_tasks` (optional `firstStep`: the student's own first step, at most 80 chars, kept by `sanitizeTask` only when set; Today's focus shows it as "Start: …" up to 2 days before the due date; an overdue task of the student's own gets Done / Tomorrow / Pick a day on that row, all through `resolveTask` (also used by the Weekly Review rollover), each with Undo), `cos_assignments` (task status map), `cos_custom_timetable`, `cos_timetable_choice`, `cos_user_batch`, `cos_hidden_subjects`.
- Attendance marks are written only by `setAttendance` (one class; an Undo toast puts the earlier mark back) and `markEndedPresent` (today's ended, unmarked classes in one write, one Undo; button on the Timetable). Same `cos_attendance` shape for both. Attendance: `cos_attendance` (daily marks), `cos_attendance_baseline`, `cos_attendance_live`, `cos_attendance_v2` + `cos_att_v2_state`, `cos_att_target`, `cos_att_reassign_log`, `cos_att_datefix_*`.
- Your aim: `cos_aims` `{ v: 1, kind: 'line'|'count'|'rhythm'|'finish', line, count, goal, times, by, scope, subjects: { CODE: pct } }` (`count` = classes a week for kind 'count', counted from Present marks Monday to today by `classesAttendedThisWeek`; `goal`/`times` = an ongoing goal's task id and check-ins a week for kind 'rhythm', shown on Today's context line via `rhythmAimStatus`; `by`/`scope` = finish date and '' or one syllabus subjectKey for kind 'finish': unticked topics + tasks due by then, with a daily pace, via `finishAimStatus`/`finishAimLine`). Ongoing goals keep `checkins: ['YYYY-MM-DD']` ("Did it today", `goalCheckIn`; kept by `sanitizeTask`, newest 120). `line` mirrors `cos_att_target` (all attendance sums still read `getAttendanceTarget()`); `saveAims` writes both. `getSubjectTarget(subj)` gives a subject's own line (saved under both its code and name, found by either, ignoring case and spaces); the rescan cleanup (`generateDeclutterPlan` → `executeDeclutterPlan`) moves lines to the matched subject like baselines, and its backup/undo carries them and is used only by the per-subject results (`getSubjectAttendanceV1`, `attV2ResultFor`). Missing `cos_aims` = built from `cos_att_target`; backups, the cloud copy and sign-in Undo carry `aims`, and old ones without it change nothing (`applyAimsFromData`). Set in Settings ("Your aim").
- Content: `cos_custom_links` (Study Vault records), `cos_syllabus`, `cos_holiday`, `cos_notice_channels` (the college portal link: `whatsappTitle`/`whatsappUrl`, edited in Settings → Profile and opened from the sidebar (laptop) or the More sheet (phone) "College portal ↗" row via `openCollegePortal()`; the old names stay for compatibility).
- Holiday mode (`cos_holiday` `{on, since, until, changedAt?}`, `until` exclusive; `changedAt` = ms stamp written by `setHoliday`, so a cloud copy older than this phone's own change does not overwrite it on sync (missing stamp = 0; restore from a backup always applies; readers ignore it); `since` may be future = planned): display-only. `isHolidayActive(date)` hides classes, class reminders and attendance; `isTaskPausedForHoliday(task)` hides ongoing tasks without the optional `keepInHoliday` flag; dated tasks always show. Today banner + Daily Briefing holiday view; `body.holiday-mode` styling (sunset masthead). During a break Today also hides the countdown (unless the exam is within 7 days), the syllabus line and Weekly Review. Ending a break that had started stores an optional `endedOn` in the off value; Today shows a one-day welcome-back card (dismissal in `cos_notified_history`). Helpers live in the "Holiday mode" block of `app.js`.
- Feedback: `cos_feedback_queue` (local only, not synced or backed up): up to 5 offline reports with a small screenshot copy each. Kept until sent (on `online` and ~4 s after start); dropped only after 5 server refusals or 14 days. Offline never counts as a try.
- Settings page (`renderSettings`): six numbered sections (Profile, Classes & attendance, Reminders, Look, Data & account, About) plus a Danger zone (clear timetable, clear tasks), with a jump list (`settingsJump`, chips on phones, contents column ≥1024px). No Save button: `settingsWire` listens on the page for `change`/`input` on the ids in `SETTINGS_AUTOSAVE_IDS` and calls `saveSettings({ quiet: true, from })` (typing waits 0.9 s), which writes the same keys as before and shows "✓ Saved" on that section instead of a toast. A new Settings field must be added to that set as well as to `saveSettings`. The About section also has a plain-text Privacy block (device storage, optional sign-in, AI scan, visit counts); keep it true if telemetry or sync behaviour changes. `cos_usage.optOut` (the usage-counts toggle) switches off both GoatCounter events and the Cloudflare visit beacon in `index.html` (read from `localStorage` before the beacon loads). `openFeedbackForm(ctx)` takes an optional `{ type, about }` that prefills the form (used by the Subject Hub's "Something look wrong here?" link via `reportSubjectProblem`); the prefilled line is plain textarea text the student can edit. Anonymous usage events are a fixed allow-list (`USAGE_EVENTS`); `week4_return` (28+ days since the first counted open) and `attendance_two_weeks` (marks in two different weeks) are worked out at app open in `trackAppOpen`, reading only the `cos_attendance` date keys and never writing attendance.
- Settings: `cos_theme`, `cos_accent` (names the palette: terracotta = Rikyū, rose = Azuki & Matcha, lavender = Ai & Kaki, apricot = Tetsu lamp; applied as `data-accent` in the head bootstrap and `initAccent`), `cos_notif_prefs`, `cos_usage`, install/push/moved prompt flags.
- Backups: `cos_cleanup_backup`, `cos_att_datefix_backup` (snapshot + undo for cleanup/migrations).
- Vault files: IndexedDB `cos_vault` (db version 1), links keep a `fileId`; small files may be data URLs in the record.
- Vault files in the account (signed in only): Firestore `users/{uid}/vaultFiles/{fileId}` holds `{name, mime, bytes, parts, at}` and `.../parts/{n}` holds `{d: Bytes}` (700 KB each). `vaultCloudSweep` runs after each good push (skipped when the local files and referenced ids haven't changed for 6 h): it uploads this device's files the account lacks (parts first, details last; at most 50 MB per account, one toast past that) and deletes a copy only when `vaultReferencedIds` lacks it and a `cos_tombstones` id names it. The synced desk record is unchanged (placeholders). On another device, a placeholder row's Download calls `vaultGetCloudFile`: reads the parts from the server, checks the size, keeps the blob in IndexedDB under the same `fileId` (then the row opens it offline via `vaultOpenFile`) and opens it. No new `cos_*` key.
- Helpers: `safeGetStorage(key, fallback)` for reads; in-memory `state` object holds tasks etc.
- Size caps: one "Size caps" block under the `KEY_*` constants at the top of `app.js` (task title/description, vault file/device/account/bulk, cloud copy warn/stop). Task caps are also applied when saved tasks are read (`sanitizeTask`), so never lower one without a migration.

## Rendering and navigation
- Example day: `onboardingSampleDay()` opens a read-only "A sample day" sheet (labelled Example, saves nothing) from the welcome example row and from the empty Today setup card ("See an example day"); focus returns to the opener.
- Paste a message or circular (Tasks; `showWhatsAppImport`, `deadline-import.js`): one review-before-save flow for WhatsApp chat exports and plain pasted text. `splitMessages` returns `plain: true` when no chat timestamps are found; the text is then split into paragraphs (or per dated line) and `app.js` accepts it, while chats need at least 2 timestamped messages (or 1 when that message has a deadline). Plain mode only: a message with a written date but no deadline word becomes a Notice row marked `unsure` that starts unticked, and a date like 11/30 that can only be MM/DD is read that way (ambiguous dates stay DD/MM). Chat parsing is unchanged. Nothing is saved until the student confirms the review list.
- Hash routing. `PAGES`: dashboard (Today), timetable, subjects, assignments (Tasks & Deadlines), calendar, resources/links/summary (Vault), settings, review. `navigate()` and the `hashchange` listener. The Notices page was retired: `notices` is not in `PAGES`, so `#notices` and `navigateTo('notices')` fall back to Today. Old `cos_notified_notices` and the `newNotices` pref are kept in storage and backups but nothing reads them.
- `renderPage(page)` switches to per-page `renderX()` that rebuilds the page with `innerHTML` strings (~90 uses; ~400 inline `onclick=` handlers). It de-dupes calls within 50 ms and saves/restores typed drafts around re-renders.
- Escaping is by hand: `escHtml_cd` (text), `escAttr_cd` (also safe inside a quoted attribute) and `jsArg_cd` (a text argument inside an inline `onclick`, e.g. `openSubjectHub(${jsArg_cd(a.subject)})`). Older per-feature copies with the same effect: `vaultEsc` (Vault), `waEsc` (WhatsApp import), `sylEsc` (syllabus; also passed to `scanners.js`). Task, subject, room, teacher, note and notice text is always escaped when rendered; `tests/verify_escaping.mjs` fails if the old raw forms come back.

## Today as a projection
- Today (`renderDashboard`) stores nothing of its own: it reads the same data as the other pages and every row leads to its source. A task row (and the task focus row) calls `openTaskFromToday(id)`: Tasks opens with that row open and in view, clearing a filter that hides it and opening its folded section. A class opens its Subject Hub; the schedule leads to Timetable, attendance to Review.
- Desktop layout (1100px and wider, CSS only in `style.css`): `#page-dashboard` is a two-column grid. `.dashboard-layout` becomes `display: contents`, so the left workbench (rows 10-11, column 1), the attendance setup question (row 10, column 2) and the right panel (row 11, column 2) share one grid. Rows 1-9 are reserved for the full-width items above them. The DOM order is unchanged (the setup card still comes before `.dashboard-layout`, which `tests/verify_onboarding_*.mjs` rely on); phones and tablets keep the single column. The Attendance panel's "Guidance" link is hidden there while no counts exist.
- Task queue: up to 4 pending tasks, late first, then by due date, then ongoing work ("Why this order?" says so); "+N more" opens Tasks.
- Study Shortcuts: up to 3 `cos_custom_links` subjects, the subject of the class now/next first, then the top task's subject (matched by `getCanonicalSubjectKey` on name or code), then saved order. Display order only.
- Quiet day (nothing pending, not on holiday, desk set up): under "All caught up" one line offers "Add the next thing that's due" (focuses the quick add) and, with a syllabus, a topic link to Subject Hubs. The exam line's "Change" opens the countdown in Settings (`openCountdownSettings`); the syllabus line's "Open" goes to Subject Hubs.
- The brief's names mapped to the real data (no shape changes): Task = `cos_custom_tasks` (`subject`, `dueDate`, `noDeadline`, `taskType`, `priority`, `firstStep`) plus the status map `cos_assignments`; class session = a slot in `cos_custom_timetable`; attendance mark = `cos_attendance[date][attendanceKeyFor(cls)]`; resource = a `cos_custom_links` record.

## Cloud sync (optional, Firestore)
- Sign-in address (`authDomain`): `claritydesk.web.app` on every host (`firebase-config.js` and `DEFAULT_FIREBASE_CONFIG`). On claritydesk.web.app it is same-site, so redirect sign-in survives Safari storage blocking; other hosts are cross-site, as they were with `campusos-83365.firebaseapp.com` (no longer used for sign-in, step 1 of retiring the campusos addresses). Needs `https://claritydesk.web.app/__/auth/handler` in the Google OAuth client redirect URIs.
- One document per user: `users/{uid}` (merge-set), plus old `users/{uid}/fcmTokens/{token}` documents from the removed FCM path (nothing reads or writes them now; left in place, no destructive cleanup). Rules: default deny; `/users/{uid}/**` owner only.
- Push: `pushLocalDataToCloud` writes profile, tasks, timetable, vault links (`linksForCloud`: uploaded files stay on device, placeholders only), statuses, attendance(+baseline/live), syllabus, theme, accent, prefs, channels, target, attendance summary, holiday, `updatedAt`. Deletes tracked via `computeSyncDeletePaths` against `cos_sync_last_pushed`. A failed delete write restores the old `cos_sync_last_pushed` and goes through `onCloudPushError`, so the next push sends it again. Size: `pushGuard` (warn 700 KB, block 900 KB) runs before each write; `lastCloudBytes` feeds the Settings sync line via `syncSizeNote`. An attendance map that is suddenly empty sends no deletes (looks like a failed read), unless an attendance Undo emptied it (`attendanceEmptiedByUndo`, memory only, cleared by the next push).
- Edit stamps: every local change to a task or vault item gets `updatedAt = nextStamp()` (`stampChanges`, called from `persistCustomTasks`/`persistCustomLinks`, which `saveCustomTasks`, `saveCustomLinks`, declutter, undo and restore use); every removed one leaves `{id, deletedAt}` in `cos_tombstones` (30 days, 200 max). Vault items have no id: key is `section|fileId-or-url|label`, so a label edit counts as delete plus add. Applying cloud data never stamps. Backups carry an optional `tombstones` list; restore stamps all restored items.
- Pull: `subscribeToCloud`: cache read first, then `onSnapshot`; both skip when `calculatePayloadHash` equals the last seen payload, else `applyCloudDataToLocalState` and re-render.
- Merge on apply (`mergeCloudIntoLocal`): tasks and vault resources merge per record (`mergeRecords`: newest `updatedAt` wins, tie or both unstamped = cloud copy, a newer tombstone removes); never a whole-list replace. The doc's `tombstones` field is merged into `cos_tombstones` (then pruned); every incoming stamp raises `cos_sync_clock` (`observeStamp`); applying never stamps. Lists keep the cloud's order, local-only records after. Vault (`mergeVaultLinks`): cloud placeholders get this device's file back first (`mergeCloudLinks`); sections in the cloud keep cloud order/name/colour (even empty); local-only sections follow, dropped only if every resource in them was deleted elsewhere. Old done tasks from the cloud are re-pruned (`pruneDoneTasks`; the 14-day prune writes no tombstones). Before a merge drops or replaces a local record, the old tasks and vault (cloud shape, no file bytes) go to `cos_sync_prev` (local only), with `lost` (each removed record as `{rec, gone}`, each replaced one as `{rec, after}` = the stamp of the version that replaced it; vault entries add `sec`, IndexedDB files keep their details, data: files become placeholders) and `open: true` when anything was lost (`recordSyncUndo`). While `open`, a later merge only adds entries, never replaces the copy; copies from before this have no `open` and offer nothing. Undo last merge: an info toast with Undo after the apply (not during the first sign-in choice, which has its own Undo), and a "Review & undo" row in Settings while the copy is open, both open `showSyncUndoReview` (lists what comes back; Put back / Keep as is / tap outside = decide later). `applySyncUndo` puts back each removed record that is not here again and each replaced record that is still the version the merge brought (later edits are kept), via `stampChanges`/`persistCustomLinks` so the restored copies win on other devices; it never removes what the merge added; on a failed write the copy stays open. Folders are made again if gone. `vaultReferencedIds` keeps the files an open copy names. A backup restore closes the copy. Works offline; the push waits for `online`. If the result has anything the cloud copy lacks, one push is scheduled (`syncToCloud`, 2.5 s debounce).
- Push guards: payload includes `tombstones`; `pushGuard` measures UTF-8 bytes (700 KB: one "getting full" toast; 900 KB: no write, "cloud copy is full" message, nothing retried); an identical payload hash to the last write is skipped (memory only, reset by any applied snapshot or failure); failed pushes retry after 5 s, 30 s, 2 min (`nextPushDelay`), then wait for the next change; a good push or `online` resets the back-off. `calculatePayloadHash` covers vault links (cloud shape) and tombstones too.
- Circuit breaker: pushes scheduled while applying cloud data (`applyingCloudData`) are capped at 3 per rolling minute (`allowApplyPush`, memory only; one console warning); once tripped it stays off for apply pushes until the next local edit (or app start). If the merge can't save the tasks or vault (storage full), nothing is pushed from that apply (this phone's old lists would replace the cloud's newer ones), `lastCloudPayloadHash` is cleared so the same cloud copy is applied on the next read, and one storage-full toast is shown per visit. The merge also compares against the cloud copy after this device's own prune/expiry rules, and tombstones have one fixed order (`byTombstoneOrder`: newest first, then id), so clock/date differences don't loop. Removing a vault section writes a `sec|<code or subject>` tombstone (`stampSections`); a section left empty by a merge is dropped if it has one, a section with resources is always kept. Duplicate sections/resources fold into one after `cos_sync_prev` keeps the unfolded copy.
- First sign-in review: when this phone and the account both have data (tasks, vault items, timetable or marks) and `cos_signin_seen` (local list of uids) lacks the uid, `signinGate` holds the cloud copy (cache read and snapshot): nothing applied, nothing pushed (`pushLocalDataToCloud` returns while held) until the student picks Keep both (the normal merge), Use my account's copy, Use this phone's copy (its differing items are stamped so they win; its timetable/marks/profile are kept and pushed), or Decide later (paused for this visit, asked again next start). The phone's data is saved to `cos_signin_backup` (local; raw stored strings, vault in cloud shape) first; if that fails only Keep both is offered. Undo (`undoSignin`) writes the backup back and asks again. Phones that synced before this (have `cos_sync_last_pushed`, no `cos_signin_seen`) are not asked. Until this phone has looked at the account's copy once (`signinSeen`: uid in `cos_signin_seen`, or in memory if storage is full), `pushLocalDataToCloud` holds any push (`signinPushWaiting`) so an edit made before the first snapshot can't overwrite the account; `markSigninSeen` then sends it. A "no doc" answer from Firestore's local cache (offline) is ignored, so an empty cache is never taken for a new account. After a choice the account is written only after its Undo toast (`SIGNIN_UNDO_MS`, 7.5 s), so Undo leaves the account as it was too. Neither key is in backups.
- Reminder presets (Settings → Reminders, `NOTIF_PRESETS`): Calm / Balanced / Off only fill the five choice selects (`taskUpcoming`, `taskOverdue`, `classReminders`, `attendanceAlerts`, `ongoingNudges`); times and `newNotices` are untouched and the stored `cos_notif_prefs` shape is unchanged. A tap saves through the normal Settings autosave, shows what changed with an Undo, and a mix that matches no preset shows "Custom" (`notifPresetOf`, `npSyncPresets`). Balanced equals the defaults in `loadNotifPrefs`.
- Sync badge: `hasPendingSync()` (signed in and `localPushPendingAt` set, cleared by the cloud's ack) shows "Waiting to sync" in `updateSyncUI`, online or offline. Otherwise a signed-in phone shows "Synced · <time>" (`lastSyncedAt`, memory only: set by a good push or a server snapshot; plain "Synced" until then); signed out stays "Saved locally". Signing out drops any first sign-in hold and closes its question. The `online` event calls `flushPendingSync()`: one push if a change is waiting (it clears `lastPushed` first), none if clean.
- Older cached app versions push unstamped records; those count as stamp 0 and lose to any stamped edit (accepted per the sync spec).
- Auth: Google (popup, redirect fallback), email link, email+password. In Settings, and from the Welcome screen's Log in. No login wall.
- Welcome (`showOnboardingModal`, full screen, value first): a quiet date line (`onboardingDateLine`, "Monday, 9 November · Today"), headline, one field + "Add something due" (`onboardingAddDue` → closes welcome, `tkQuickAdd` review form), "Paste a message" (`onboardingPasteMessage` → `showWhatsAppImport`; `onboardingTakePhoto` ("Use a photo as reference") → camera/gallery picker, a check sheet, then the Add Task form with the photo pinned in it (`onboardingPinReference`); the photo is an in-memory object URL, never saved, dropped when the form closes, since tasks have no attachment field and nothing reads photos), a "Coming up" row (`onboardingComingUpHtml`: the student's next real dated task, else a tappable row labeled Example that calls `onboardingSampleDay`: a read-only sample-day sheet over the welcome, welcome inert meanwhile, focus back to the row, nothing saved and `cos_onboarding_dismissed` untouched), optional Set up my timetable (`showAddTimetableChoice`) / Study without a timetable (`setupSelfStudy`), then the footer line (plus the anonymous-visit count note when `usageActive()`), then quiet Show me around / I already have an account (Log in). Show me around → name step (`onboardingShowName` / `onboardingSaveName`, optional, saves `profile.name`) → `onboardingStartTour()` closes the welcome and `import()`s `welcome-tour.js` (`startTour({ name, track })`: dims the live page and lights one real bottom tab or sidebar item at a time, last stop is the timetable card; precached by `sw.js` so it works offline). Today then asks one thing at a time: no timetable → one card (`showAddTimetableChoice()`: photo `setupScanTimetable` or typing `setupAddClasses`; quiet `setupSelfStudy` link) → lab group card (`onbPickGroup`, opens the existing `showDeclutterDeskModal` review when other groups' classes remain) → name inside the greeting if still missing (`onbSaveGreetingName`) → from the day after the timetable appeared, attendance card (`showBaselineModal`, `onbAttLater`, bunk calculator behind `onbShowBunk`). Skip/Later and the first timetable day are `onb_*` keys in `cos_notified_history` (kept by `pruneNotifiedHistory`; not in backups, so a restore may ask a skipped card again; Later stores one `onb_att_later` date); `onb_tt_day` is written on `saveTimetable`, on open and at a new day, never while rendering. Events: `welcome_choice`, `name_given`/`name_skipped`, `tour_step`/`tour_done`/`tour_skipped`.

## AI and OCR
- On-device first: Tesseract.js from jsDelivr (lazy), deterministic grid reconstruction and normalisation, then AI vision via `AIService` through the proxy. `AIService._cooldowns` skips recently failed providers.
- Parser/OCR/AI output goes to editable review screens before any write.
- Before any timetable, attendance or syllabus photo is read, `confirmScanPhotoQuality` (`app.js`) checks it on the device (too small, or too little detail = blurry/washed out; thresholds measured on the test kits, checked by `npm run test:photo-check` in CI). A flagged photo gets "Choose another photo" (reopens the picker) or "Scan this photo anyway"; PDFs and photos that pass go straight through.
- Attendance photo scan and syllabus scan live in `scanners.js` (`createScanners(deps)`). `app.js` keeps the file pickers (so `input.click()` stays inside the tap), imports the module on first scan or when the scan tab opens (`loadScanners()`), and routes the window handlers through `callScanner()`, which shows a toast if the file can't load. `AIService` stays in `app.js`. If an AI-read attendance row's four counts don't add up to its printed Total Count, `extractAttendanceRowsViaVision` asks the next provider too (`extractStructuredFromImage`'s `skipProviders`) and keeps the answer with fewer such rows, never one with fewer courses; rows still off stay flagged in review. Before review, `flagAttendanceRowsThatWentBack` flags a subject whose present count or classes held is lower than its saved baseline (`cos_attendance_baseline`, read only), unless most subjects went down (a new term).
- Timetable photo reading lives in `timetable-ocr.js` (`createTimetableOcr(deps)`): deskew, preprocessing, the 2D grid / line / text-stream parsers, `extractTimetableFromImage` and the Vision AI grid prompt and row clean-up. The vision call starts right after the first Tesseract pass (its image and prompt only need that pass) and runs alongside the on-device retries (Stages A-D); it is awaited only if the on-device result fails the confidence gate, otherwise its answer is ignored. A vision answer from a backup provider (not Gemini) returns `needsReview: 'backup-ai'`, and the review screen asks for every row to be checked. `app.js` keeps a same-named async `extractTimetableFromImage` that loads it (`loadTimetableOcr()`, started when the picker opens) and turns a failed load into the error screen, where Retry works. `AIService`, the Tesseract loader, subject normalization, the legend parsers and `groupWordsIntoLines` / `mapRawOcrWordsForDetection` / `correctDigitLetterConfusion` stay in `app.js` because other code uses them.
- Ask Desk (`ClarityAssistant`, in `desk-assistant.js`): rule-based intents on local data, no model. `app.js` imports it on first use (`loadClarityAssistant()`) and passes its helpers in via `clarityAssistantDeps()`; tests load it with `tests/lazy-modules.mjs`. Guided buttons open existing flows; no direct writes from chat.

## Reminders
- Foreground: timers in `app.js` (one `setInterval`) plus local Notification API.
- Gentle nudges for ongoing (no-deadline) tasks: foreground only, opt-in. Optional `cos_notif_prefs` fields `ongoingNudges` (`off` default | `daily` | `every_2_days` | `weekly`) and `ongoingNudgeTime` (`HH:MM`, default 18:00); older saved prefs load unchanged. Rule 6 in `checkScheduledNotifications`: at most one nudge a day, from the chosen time to 3 hours after it (`ongoingNudgeDue`), one task per nudge rotating (`pickOngoingNudgeTask`), wording from `buildOngoingNudge` (never due/overdue). Skips tasks resting in holiday mode. Markers `ongoing_last_date` / `ongoing_last_task` live in `cos_notified_history` (kept by `pruneNotifiedHistory`). The Settings save handler rebuilds the whole prefs object, so any new pref must be added there too. Locked by `tests/verify_ongoing_nudges.mjs`.
- Closed app: device registers with `push-worker`; reminders are sent from D1 by a Cloudflare cron. The old Firebase (FCM) push path (client, `sw.js` handler, GitHub job) was removed on 2026-10-28; `sw.js` loads no third-party scripts.
